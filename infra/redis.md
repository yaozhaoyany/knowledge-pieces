我对redis的了解很少，麻烦详细帮我讲解哨兵模式跟集群模式的区别，优势劣势，以及为什么要做这些技术选型

这是一个非常重要的技术选型知识点！Redis 的两种高可用模式在面试中也是超高频考题。我来帮你彻底讲透。

首先：Redis 单机模式有什么致命缺陷？
一台 Redis 挂了，整个缓存层就瘫痪了。所有请求瞬间击穿到数据库，这就是"缓存雪崩"。所以我们必须引入高可用机制。Redis 官方提供了两种截然不同的方案：

方案一：Sentinel（哨兵）模式
一句话概括：一组"保镖"盯着主节点，主节点一死，保镖立刻扶从节点上位。

架构拓扑：

┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Sentinel #1 │     │ Sentinel #2 │     │ Sentinel #3 │
│  (监控者)    │     │  (监控者)    │     │  (监控者)    │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       ▼                   ▼                   ▼
┌─────────────┐     ┌─────────────┐
│ Redis Master│────▶│ Redis Slave │   (主从数据同步)
│  (读+写)    │     │  (只读)     │
└─────────────┘     └─────────────┘
工作原理：

3 个 Sentinel 进程不断对 Master 发心跳（PING）
当超过 2 个 Sentinel 都认为"Master 已经挂了"（票数过半才行，防止误判），触发自动故障转移 (Failover)
Sentinel 选一个 Slave 升级为新 Master，并通知所有客户端"新老板上任了，以后找他"
整个切换过程秒级完成
核心特征：所有数据存在一台机器上，Slave 只是 Master 的镜像备份。

方案二：Cluster（集群分片）模式
一句话概括：把数据切碎，分散存到多台机器上，每台只管一部分。

架构拓扑：

┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  Master A    │   │  Master B    │   │  Master C    │
│ Slot 0~5460  │   │ Slot 5461~   │   │ Slot 10923~  │
│              │   │   10922      │   │   16383      │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │                  │                  │
       ▼                  ▼                  ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  Slave A'    │   │  Slave B'    │   │  Slave C'    │
└──────────────┘   └──────────────┘   └──────────────┘
工作原理：

Redis 把整个 Key 空间切成 16384 个槽位 (Slot)
每台 Master 负责一段槽位。比如你 SET order:123，Redis 对 Key 算 CRC16 哈希，结果落在第 8888 号槽位，那就路由到 Master B
每台 Master 自带一个 Slave 做热备
某台 Master 挂了，它的 Slave 自动顶上（不需要外部 Sentinel）
核心特征：数据被分散到多台机器，总容量 = 所有 Master 的内存之和。

灵魂对比
维度	Sentinel 哨兵	Cluster 集群
数据分布	全量数据在一台 Master 上	数据被切片分散到多台 Master
最大容量	受单机内存限制（比如 64GB）	理论无上限（加机器就行）
读写能力	写只能走 Master，读可分流到 Slave	每个分片都能独立读写，吞吐量线性增长
故障转移	依赖外部 3 个 Sentinel 投票	内置选举，不需额外进程
客户端复杂度	简单，连 Sentinel 拿 Master 地址即可	复杂，客户端要理解"Slot 路由"和 MOVED 重定向
运维复杂度	低（3+2 = 5 个进程）	高（至少 6 个进程，扩缩容要数据迁移）
适用数据量	数据量 < 单机内存（通常 < 64GB）	数据量远超单机内存（TB 级）
为什么我们的项目选 Sentinel 而不是 Cluster？
结合我们的"高可用订单搜索系统"的业务场景来做选型分析：

数据量小：我们用 Redis 做的是订单缓存热 Key 和接口幂等锁，数据量远不到 TB 级，单机内存绰绰有余。
本地资源有限：你的 Kind 集群一共就 2 个 Worker 节点。Cluster 模式最少要 3 主 3 从 = 6 个 Pod，直接把你电脑榨干。Sentinel 模式只需 1 主 1 从 + 3 个轻量哨兵，友好得多。
客户端 Spring Boot 集成简单：Java 的 Lettuce / Jedis 客户端连 Sentinel 只需配一个 spring.redis.sentinel.master 就搞定了。连 Cluster 则需要额外处理 Slot 路由和跨分片事务的限制。
什么时候必须上 Cluster？
当你的业务增长到某一天，一台 Redis 的 64GB 内存已经装不下所有的热数据了（比如电商大促时几十亿条商品缓存），那就必须水平扩展到 Cluster 模式，靠"切片"把数据摊到几十台机器上。

一句话总结：Sentinel 解决的是"高可用（不挂）"问题；Cluster 解决的是"高可用 + 大容量（不挂且装得下）"问题。数据量没爆之前，Sentinel 永远是性价比最高的选择。

问题 1：Redis Cluster 的选举机制
节点怎么知道别人挂了？—— Gossip 协议（八卦协议）

Redis Cluster 里的每个节点，都会每秒钟随机挑几个邻居节点发一次 PING。如果某个节点在 cluster-node-timeout（默认 15 秒）内没有回复 PONG，发送者就标记它为 PFAIL（主观下线 - Probable Fail）。

但单个节点说了不算！因为可能只是它俩之间的网线被老鼠咬了。 所以这个"八卦"会随着 Gossip 消息扩散到整个集群。当超过半数的 Master 节点都报告同一个节点 PFAIL 时，该节点升级为 FAIL（客观确认下线）。

选举怎么进行？—— 类 Raft 投票

当 Master B 被确认 FAIL 后：

Master B 的 Slave B' 发现自己的老大挂了，立刻向集群中所有存活的 Master 节点发起投票请求："我要当新 Master B，同意吗？"
每个 Master 在同一轮选举里只能投一票（先到先得）
当 Slave B' 收集到超过半数 Master 的同意票后，它立刻自我升级为新 Master B，接管原来 Master B 负责的那段 Slot
然后通过 Gossip 广播通知全集群："新 Master B 上线了，以后 Slot 5461~10922 的请求找我！"
极端情况： 如果你只有 3 个 Master，挂了 2 个，剩下的 1 个凑不够"过半票数"，整个集群就会拒绝服务。这就是为什么 Redis Cluster 最少要 3 主 3 从。

问题 2：客户端怎么连 Redis Cluster？有没有统一入口？
残酷真相：Redis Cluster 原生没有统一的网关入口！

客户端的连接流程是这样的：

第一次连接（握手发现阶段）：

客户端随便连上集群中的任意一个节点
发送 CLUSTER SLOTS 命令，拿到一张完整的 Slot 路由表（哪些 Slot 归哪个 Master 管）
客户端把这张路由表缓存在自己本地内存里
日常读写：

客户端要写 SET order:123 {...}
客户端自己在本地算 CRC16("order:123") % 16384 = 8888
查本地路由表：Slot 8888 归 Master B，于是直接把请求发给 Master B
路由表过期了怎么办？（最精彩的部分） 如果集群刚做完扩缩容，Slot 迁移了，客户端的本地缓存还是旧的：

客户端发请求到老 Master B，Master B 发现："这个 Slot 不归我管了！"
返回一个特殊错误：MOVED 8888 192.168.1.5:6379（告诉你新地址）
客户端收到 MOVED，刷新本地路由表，然后重定向到正确的节点
业务应用需要做什么？ 好消息是：几乎什么都不用做！ 现代 Redis 客户端（Java 的 Lettuce、Jedis）已经把上面的 Slot 路由、MOVED 重定向、路由表刷新全封装好了。你只需要把连接模式从 standalone 改成 cluster，并提供几个种子节点地址即可：

yaml
# Spring Boot application.yml
spring:
  redis:
    cluster:
      nodes:
        - master-a:6379
        - master-b:6379
        - master-c:6379
但有一个坑： 跨 Slot 的事务和 Pipeline 是被禁止的！如果你一次操作涉及的多个 Key 被哈希到了不同 Slot（也就是散落在不同的物理机器上），Redis 直接报错。解决办法是用 Hash Tag——在 Key 里加花括号 {order}:123 和 {order}:456，Redis 只对花括号里的部分算哈希，这样同一个业务实体的所有 Key 都落在同一个 Slot 上。

问题 3：主从数据同步的一致性问题
你说得完全对！Slave 读到的确实可能是老数据！

Redis 的主从复制是异步的 (Asynchronous Replication)。完整链路是：

客户端 --写--> Master (写入内存，立刻返回 OK)
                  │
                  ├── 同时，Master 把写命令追加到 replication buffer
                  │
                  └── 异步发送给 Slave（通常延迟在毫秒级）
                            │
                            └── Slave 收到并重放命令，数据最终一致
关键：Master 返回 OK 给客户端的瞬间，Slave 还没收到这条数据！

这个时间窗口通常只有几毫秒到几十毫秒，但在以下灾难场景中会造成数据丢失：

客户端写了一条数据到 Master，Master 返回 OK
Master 还没来得及把这条数据同步给 Slave，突然宕机
Slave 被提升为新 Master
那条数据永远消失了——因为它只存在于已经死去的旧 Master 的内存里
Redis 有办法解决吗？

方案	怎么做	代价
WAIT 命令	写入后执行 WAIT 1 5000（等至少 1 个 Slave 确认收到，最多等 5 秒）	写性能暴跌，从微秒级变成毫秒级
min-replicas-to-write	配置项：如果存活的 Slave 少于 N 个，Master 直接拒绝写入	可用性降低
接受现实	承认 Redis 天生就是 AP 系统（高可用 + 最终一致），不是 CP 系统	无
大厂的务实选择： 绝大多数公司选择"接受现实"。因为 Redis 的定位从来就不是"绝对不丢数据的持久化数据库"，它是高速缓存层。真正不能丢的数据写在 PostgreSQL 里。Redis 丢了几毫秒的缓存？大不了下一次请求 Cache Miss，重新从 PG 查一遍填回来就好了。

一句话总结：Redis 主从复制牺牲了强一致性，换来了极致的写入性能（微秒级响应）。这是 CAP 定理在实战中最经典的 Trade-off 体现。

既然 Redis 追求的不是高可靠性，为什么还要配持久化？
你的质疑直击要害！ 我那条注释确实写得有误导性。让我纠正并给你讲清楚真实原因。

首先要澄清：那两个 persistence.size 配置其实不是在开启"AOF 持久化策略"，它们是在给 K8s 的 PVC（持久化卷）分配磁盘大小。

但核心问题不变：一个内存数据库，为什么要往磁盘上写东西？

答案是：持久化不是为了"永不丢数据"，而是为了"重启后不用从零开始"。

想象以下场景：

有无持久化	Redis Pod 被 K8s 重新调度（杀掉重建）后会发生什么
无持久化	新 Pod 启动后，内存是空的。10GB 的缓存数据全部蒸发。 瞬间所有请求击穿到 PostgreSQL，PG 被几万 QPS 当场打崩 = 缓存雪崩
有持久化	新 Pod 启动后，从磁盘上的 RDB/AOF 文件恢复数据。虽然可能丢失最后几秒的写入，但 99.9% 的缓存数据还在，业务平稳过渡
所以持久化的真正价值不是"可靠性"，而是"快速恢复能力 (Fast Recovery)"。

Redis 提供了两种持久化策略：

策略	原理	恢复速度	数据完整度
RDB (快照)	每隔 N 秒对内存做一次全量快照，写成一个压缩的二进制文件	极快（直接加载二进制）	可能丢失最后一次快照之后的所有写入（可能是几分钟）
AOF (追加日志)	每条写命令都追加到一个日志文件（类似数据库的 WAL）	较慢（要重放所有命令）	几乎不丢（可配置为每秒刷盘或每条刷盘）
在 K8s 环境下，持久化还有第二层意义： K8s 的 Pod 是"朝生暮死"的，随时可能被调度器杀掉搬到另一台 Worker 节点上。如果 Redis 的数据只存在容器内存里，Pod 一死数据就没了。但如果挂载了 PVC（你配的那个 1Gi 磁盘），数据就写在了宿主机的物理磁盘上。即使 Pod 被杀掉重建，新 Pod 挂上同一块 PVC，数据就回来了。

一句话总结：Redis 的持久化不是为了像 PostgreSQL 那样做到"一条数据都不丢"的 ACID 保证，而是为了在进程重启、Pod 重调度等日常运维事件中，避免缓存层从零预热导致的雪崩灾难。

正确的场景：同一笔订单的多个属性
假设用户下单后，你要在 Redis 里同时操作属于同一笔订单的多个缓存 Key：

MULTI
SET   order:123:status    "PAID"          # 订单123 的状态
SET   order:123:pay_time  "2026-03-25"    # 订单123 的支付时间
INCR  order:123:retry     1               # 订单123 的重试次数
EXEC
这三个 Key 在业务上是天然的强关联——它们都属于同一笔订单 123。你需要它们要么全部更新，要么全不更新。

问题来了：在 Redis Cluster 里，这三个 Key 的哈希结果可能完全不同：

CRC16("order:123:status")   % 16384 = 5201  → Master A
CRC16("order:123:pay_time") % 16384 = 9877  → Master B
CRC16("order:123:retry")    % 16384 = 2103  → Master A
status 和 retry 运气好落在了同一台，但 pay_time 跑到了另一台。事务直接报错 CROSSSLOT。

Hash Tag 怎么解决？
把 Key 改造成这样：

MULTI
SET   {order:123}:status    "PAID"
SET   {order:123}:pay_time  "2026-03-25"
INCR  {order:123}:retry     1
EXEC
Redis 看到花括号后，只提取 {order:123} 这个子串去算哈希，完全忽略花括号外面的 :status、:pay_time、:retry：

CRC16("order:123") % 16384 = 8888  → 三个 Key 全部落在 Master B！
Key 的业务语义完全不变——{order:123}:status 读起来仍然是"订单 123 的状态"。花括号只是告诉 Redis 的路由引擎"别看后缀，你只需要看花括号里面的部分来决定这条数据存哪台机器"。

所以 Hash Tag 的本质是什么？
它不改变数据的含义，只改变数据的路由策略。

花括号是给 Redis Cluster 路由引擎看的"暗号"：

没有花括号 → Redis 对整个 Key 字符串算哈希 → 同一个业务实体的不同属性可能散落在不同机器
有花括号 → Redis 只对花括号内的部分算哈希 → 同一个业务实体的所有属性保证落在同一台机器 → 事务和 Pipeline 畅通无阻








那路由策略里为什么要 % 16384，这代表redis上限只能存储16384个条目吗，然后分配到不同的cluster

绝对不是！ 16384 是槽位 (Slot) 的数量，不是数据条目的上限。这两个概念完全不同。

Slot 是什么？—— 数据的"邮编"
你可以把它想象成中国的邮政编码系统：

全国有大约 100 万个 邮政编码
但中国有 14 亿人
邮编不是限制你能住多少人，而是决定"你的信寄到哪个邮局去分拣"
Redis Cluster 同理：

一共有 16384 个 Slot（邮编）
但你可以存 几十亿条 Key（居民）
每个 Key 通过哈希被分配到一个 Slot（邮编），然后 Slot 再映射到具体的 Master 节点（邮局）
几十亿条 Key → 哈希取模 → 均匀散落到 16384 个 Slot 里 → 每个 Slot 平均装着几十万条 Key
                                                            ↓
                                                    3 台 Master 平均每台管 ~5461 个 Slot
所以一个 Slot 里面可以装无限多条 Key（只受内存限制），16384 只是决定了"有多少个桶来分配数据"。

为什么偏偏是 16384 这个数字？
这是 Redis 的作者 antirez 亲自解释过的工程权衡：

原因 1：Gossip 心跳包的大小 Redis Cluster 的每个节点在发送 Gossip 心跳时，需要携带一个位图 (Bitmap)，标记"我负责哪些 Slot"。

16384 个 Slot → 位图大小 = 16384 / 8 = 2KB（每个心跳包多带 2KB，完全可以接受）
如果改成 65536 个 Slot → 位图大小 = 65536 / 8 = 8KB（每个心跳包都多带 8KB，在大规模集群中网络开销会膨胀得非常恐怖）
原因 2：集群规模的上限 Redis 官方建议 Cluster 的 Master 节点数量不超过 1000 台。 16384 / 1000 ≈ 16 个 Slot/节点——每台机器至少分到十几个 Slot，颗粒度足够细，扩缩容时 Slot 迁移非常灵活。 如果 Slot 太少（比如只有 100 个），那你有 50 台 Master 时每台才 2 个 Slot，迁移起来颗粒度太粗，负载很难均衡。

一句话总结：16384 是一个精心计算的数字——大到足以让上千台机器灵活分配，小到每次心跳只多花 2KB 网络流量。它跟你能存多少数据毫无关系，你的存储上限永远只取决于你有多少台机器和多少内存。

Redis 为什么支持 Lua？
Redis 虽然有 SET、GET 这些原子命令，但当你需要把多个命令组合成一个不可分割的原子操作时，单条命令就不够用了。

经典场景：分布式限流（每秒最多允许 100 次请求）

如果用普通命令：

GET  rate:user:123          # 第1步：读当前计数
# ← 这个间隙里，另一个请求可能也读到了同样的值！（竞态条件）
INCR rate:user:123          # 第2步：计数+1
两步之间有时间窗口，高并发下会出现竞态条件。但用 Lua 脚本就能一步搞定：

lua
-- 这段 Lua 脚本在 Redis 内部原子执行，中间不会被任何其他命令打断
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], 1)  -- 第一次访问时设置1秒过期
end
if current > 100 then
    return 0  -- 超过限流阈值，拒绝
end
return 1      -- 放行
Lua 在 Redis 里的核心价值
特性	说明
原子性	整个 Lua 脚本在 Redis 单线程中一口气执行完，不会被其他命令插队
减少网络往返	把 5 条命令打包成 1 个脚本，只需 1 次网络请求（而不是 5 次）
常见用途	分布式锁、限流器、库存扣减、幂等性校验
